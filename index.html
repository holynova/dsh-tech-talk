为什么需要 Harness？别再魔改“精装房”

  • 发动机 vs 底盘：模型负责想，Harness 负责把能力落地干活
  • 痛点 1（换底座）：本地读写切进远程沙箱，核心耦合难改
  • 痛点 2（长对话）：原地截断消息数组，既丢历史又打穿缓存
  • 痛点 3（改循环）：一步步调工具太慢，想换执行模式只能 Fork
dsh 的思路：不做改不动的精装房，做成连核心都能热插拔的底盘。

核心理念：什么是真正的“万物皆插件”？

维度 传统 Agent 框架 DeepSeek Harness (dsh)
架构隐喻 主板焊死，仅留 USB 外设口 乐高底板 / 微内核，全模块平权
可换范围 Tools、MCP、少量钩子 模型、文件、工具、日志、UI、Agent Loop
核心特权 庞大且硬编码的 Core 无特权核心（底层只有薄 Cordis 容器）
定制方式 Fork 仓库魔改，难跟上游升级 写一份 cordis.patch.yml 覆盖或插入
  • 平权设计：系统内置模块与自研插件地位完全一致
  • 按需拼装：同一套底座，配出 Web、Headless、SDK 三种形态
  • 运行热插拔：插件按依赖自动挂载，卸载时自动清理资源

Profile 与 Patch：插件树是怎么一层层“补丁”出来的？

~/.dsh/profiles/web/cordis.patch.yml PATCH YAML 
# 1. 按 id 覆盖已有插件配置（注意：整块替换 config）
- id: system-prompt
  config:
    personaPrefix: "你是团队研发助手，改代码前先跑单测。"

# 2. 替换某个内置能力（例如把本地 fs 换成沙箱版）
- id: fs-provider
  name: '@my-org/dsh-fs-sandbox'

# 3. insert：往插件树里挂载新插件
- insert:
    - id: my-metrics
      name: '@my-org/dsh-metrics-plugin'
      config: { strict: true }
调试最终合并结果 CLI 
dsh --profile web --dump-config   # 一键打印合并后的完整配置树
  • 不改源码：所有定制都写在 cordis.patch.yml
  • 按 id 定位：支持改配置、换实现、insert 挂新插件
  • 避坑提示：config 是整块替换（非深度合并），随时用 --dump-config 核对

Python SDK 接入示例 PYTHON 
from dsh import DSHClient

# 连接本地 dsh 服务，或托管 stdio 子进程
client = DSHClient("http://127.0.0.1:3080")
session = client.create_session()
for event in session.send("总结这个仓库的核心模块"):
    print(event)

  • Headless 模式：无 UI 单次运行，直接接进 CI / 定时任务
  • SDK 模式：通过 JSON-RPC 跨语言调用，嵌入业务系统

原理一：Cordis 依赖注入（DI）+ effect 自动清理

sync-plugin.ts TypeScript · 13 Lines 
import type { Context } from '@deepseek-ai/cordis'

export const name = 'rules-sync'

// 1. 依赖注入（DI）：声明我需要哪些服务
export const inject = ['fs', 'tools']

export function apply(ctx: Context) {
  // 2. 可逆副作用：挂载时执行，卸载/热更新时自动清理
  ctx.effect(() => {
    const timer = setInterval(() => syncRules(ctx.fs), 60_000)
    return () => clearInterval(timer)
  })
}
  • 解耦获取服务（DI）：不直接 import 实现类，通过 ctx 按名注入
  • 动态依赖拓扑：类似 Spring DI，但支持运行时热上线与级联下线
  • 免写判空：依赖没就绪就挂起等待，进 apply 时服务必可用
  • ctx.effect 兜底：副作用统一返回清理函数，热插拔零泄漏

系统内置 Definition · @deepseek-ai/dsh-fs CONTRACT 
import { Service } from '@deepseek-ai/cordis'

// 系统只声明“文件服务长什么样”，不绑定本地硬盘
export abstract class FsService extends Service {
  static name = 'fs'

  abstract readFile(path: string): Promise<string>
  abstract writeFile(path: string, content: string): Promise<void>
  abstract listDir(path: string): Promise<string[]>
}

// 声明 ctx.fs 类型，所有插件都能通过 DI 拿到它
declare module '@deepseek-ai/cordis' {
  interface Context { fs: FsService }
}
重写实现 Provider · my-sandbox-fs.ts OVERRIDE 
import { FsService } from '@deepseek-ai/dsh-fs'

// 继承同一个 Definition，把读写限制在远程沙箱
export class SandboxFsService extends FsService {
  async readFile(path: string) {
    return remoteContainerRead(guardPath(path))
  }
  async writeFile(path: string, content: string) {
    if (path.endsWith('.env')) throw new Error('禁止写密钥')
    return remoteContainerWrite(guardPath(path), content)
  }
  async listDir(path: string) { return remoteList(path) }
}
  • 面向接口解耦：系统核心能力（文件、命令、运行时）都采用这种接缝结构
  • 一行 Patch 替换：在 cordis.patch.yml 里换掉 Provider，上层工具与模型零修改

原理三（续）：什么是 Projection？一份流水，多种视图

  • 大白话类比：Log 是“银行流水”，Projection 是按需算出的“账单 / 余额 / 报表”
  • 两类事件分流：带 surfaceOp 的进模型对话；纯日志（流式碎片）只给 UI 与调试
  • 强一致保证：发给 LLM 的消息严格等于 deriveMessages() 算出的结果
  • 插件可扩展：写个纯函数 apply(state, event) 就能派生自己的进度 / 统计面板

核心全流程：4 步看懂一条指令怎么跑完

  • 主干极简：就是“进日志 → 投影调模型 → 跑工具 → 记结果”的闭环
  • Loop 可换：默认一步步调工具，也可一键切换成 PTC 模式（下一页）
  • 处处可插：模型、工具、文件服务、日志、UI 每一环都是插件

进阶玩法：PTC 模式——让模型写代码批量调工具

模型一次生成的 run_code（沙箱执行） TypeScript 
// 例：扫描 src/ 下所有含 TODO 的文件，只返回命中列表
const files = await fs.listDir('src/')
const hits = await Promise.all(
  files.filter(f => f.endsWith('.ts')).map(async (f) => {
    const txt = await fs.readFile(f)
    return txt.includes('TODO') ? f : null
  })
)
return hits.filter(Boolean) // 只把结果返回上下文
  • 工具变 SDK：把工具生成 .d.ts 声明注入给模型，直接写 TS 调用
  • 省时省 Token：海量中间结果留在沙箱过滤，只带精简结论回来
  • 安全可控：dsh-tool-executor-ptc 内置并发数、频率上限与超时熔断
  • 无缝切换：靠前面讲的插件架构，换掉执行器插件即可开启 PTC

落到代码：写一个 dsh 插件长什么样？

index.ts TypeScript · 16 Lines 
import type { Context } from '@deepseek-ai/cordis'
import Schema from '@deepseek-ai/schemastery'
import { defineTool } from '@deepseek-ai/dsh-tools'

export const name = 'metrics-inspector'
export const inject = ['tools']
export interface Config { endpoint: string; strict: boolean }

export const Config = Schema.object({
  endpoint: Schema.string().required(),
  strict: Schema.boolean().default(true),
})

export function apply(ctx: Context, cfg: Config) {
  ctx.tools.register(defineTool({
    name: 'query_metrics',
    parameters: Schema.object({ svc: Schema.string() }),
    execute: ({ svc }) => fetchMetrics(cfg.endpoint, svc),
  }))
}
  • inject：声明依赖注入，自动拿到 ctx.tools
  • Schema：配置自动校验，Web 端同步生成表单
  • defineTool：自动校验入参，直接暴露给模型
  • apply(ctx)：挂载生效，卸载自动回收副作用
会写 TypeScript 函数，10 分钟就能写出并热加载你的第一个插件。

现场高频 Q&A 速查

1. 这跟 MCP 有什么区别？
层级不同、完全互补。MCP 是“USB 外设协议”，只管接入外部工具/数据；dsh 是“微内核主板”，MCP 只是 dsh 里可接入的一类插件，dsh 还管 Loop（含 PTC）、Session 日志与投影、文件/沙箱服务和 UI。
2. 跟 Claude Code / LangGraph 怎么选？
Claude Code 是开箱即用的精装成品；LangGraph 偏有向图工作流编排；dsh 主打“可深度二次开发、热插拔组合的 Agent 底盘”，适合重写内置服务、切换 PTC 模式和团队插件沉淀。
3. 全插件化会不会难 Debug？
三板斧定位：① dsh --dump-config 一键看 Patch 后的完整配置；② inject 显式声明依赖，缺失服务启动即报错；③ Append-Only Session Log 完整记录每步事件，随时回放。
4. 影子压缩会丢上下文吗？
压缩摘要本身有损，但底层原始事件从未物理删除，UI 展开查看或按需回查原始片段都 100% 保留。
5. 只能用 DeepSeek 模型吗？
完全模型无关（Model-Agnostic），模型路由本身也是插件，支持 DeepSeek 原生以及 OpenAI / Anthropic 兼容端点。
